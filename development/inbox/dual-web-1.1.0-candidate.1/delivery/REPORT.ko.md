## 실제 로컬 HTTP 측정

같은 원본 네 개(manifest, routes, canon, evidence)를 비교했다. 새 방식의 첫 요청에는 안내를 찾는 요청도 포함했다. 비압축 HTTP 응답의 실제 본문 바이트를 측정했다.

| 방식 | HTTP 요청 수 | 응답 본문 바이트 |
|---|---:|---:|
| 기존 개별 읽기 · 첫 요청 | 4 | 2,584 |
| 안내+묶음 · 첫 요청 | 2 | 5,133 |
| 기존 개별 읽기 · 재검증 | 4 | 0 |
| 안내 재검증+보관 묶음 재사용 | 1 | 0 |

첫 읽기의 요청 수는 4→2, 재검증은 4→1이다. 재검증 조건에서 본문이 바뀌지 않으면 양쪽 모두 0바이트였고, 새 방식은 안내 요청 하나 뒤 보관한 묶음을 재사용했다.

**작은 예제에서 첫 본문 전송량은 오히려 늘었다.** 묶음의 역할·경로·해시와 별도 안내 정보가 추가되기 때문이다. 따라서 이번 결과를 '트래픽 전체 절감'이나 '서버 비용 절감'으로 보고하지 않는다. 직접 확인된 것은 요청 묶기, 변경 여부 확인, 원문 보존, 재사용 가능한 전달 동작이다.

요청·응답 헤더, TLS·패킷, 지연 시간, 실제 CDN·원본 서버 부하·요금은 측정하지 않았다. 유효한 로컬 캐시가 있으면 기존 방식도 새 요청을 하지 않을 수 있다. 모든 최적화된 HTML/API 방식보다 우수하다는 비교도 수행하지 않았다.
